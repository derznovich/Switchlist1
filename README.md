# Trainz Switchlist Program

By Wasted Tris / Derznovich

## Introduction: purpose and philosophy of the switchlist program

In my own Trainz gameplay, for many years I used a spreadsheet to
generate random industry tasks. However, managing a spreadsheet became
cumbersome, because I would have to continually refer to the spreadsheet
on a second screen, often taking attention away from the game. I created
this switchlist program to generate random tasks and handle industry
chains (spot empties, pickup loads, deliver loads), track the completion
of tasks, and generate a user score.

The goal is not to simulate dispatching minute-by-minute. Instead, the
program generates realistic freight demand over a multi-day operating
session while allowing the player complete freedom in how they
accomplish the work. Tasks can be ignored, postponed, reprioritized, or
manually overridden. The switch list is intended to guide operations
rather than dictate them.

The routes I play are typically large or medium-large, starting with the
Pennsylvania & Berwind by Approach Medium. These have dozens of
industries and around 100 potential industry-commodity pairs. The
switchlist program will not require you to activate all of these, only a
random subset. You can customize this by editing the switchlist program
and industry list.

Important: the switchlist is designed to service industries where all
production and consumption are independent and unconstrained. Thus, it
differs from Trainz Living Railroad, where an industry may need certain
inputs like iron ore + coal and only with the right ratio of inputs will
steel be available for pickup. I recommend setting up your route with
the JR Multi Industry II and making each commodity's consumption or
production independent, such that the commodity it produces is always
showing a full queue, and the commodity it consumes is always an empty
queue. Hence, the track should always load or unload compatible cars and
commodities, and you only follow the instructions of the switchlist.
Like a real railroad, basically.

The program does not interact directly with Trainz or Trainz sessions,
but acts as an independent overlay. You will need to set up your own
industry and commodity list, and each time you want to play, you will
run the switchlist program in python. Since there is no interaction with
Trainz, updates to Trainz do not affect the program. You can play Trainz
with or without the program running at the same time. The score
generated by the program will not appear in game. While the program is
designed to track and score your progress, you will mark the tasks as
completed or active on your own -- Trainz and Trainz sessions will not
interact with the program in any way. Hence, the program is oriented
towards self-directed gameplay.

Similarly, the program does not interact with portals or other
third-party software / session rules such as CMTM. Unlike CMTM, which
tracks individual freight cars and requires industries to be configured
around its operating system, this switchlist does not track individual
cars or interact directly with Trainz industries. It simply generates
movements for car types and commodities based on the industry list,
leaving the player free to choose which compatible cars to use and how
to carry out the work.

You may send trains to portals where they leave the map, but when you
require trains to enter the map to bring in loads, you will have to set
those up in Surveyor with the appropriate cars matched to the
commodities served on your route and with the switchlist / industry
spreadsheet. If you use Cartagger V3 (optional), you can tag the cars
yourself on the fly, but the program will not do this for you.

## Basic gameplay outline

1.  Run `switchlist1.py` and select New Session.
2.  Run `switchlist_viewer.py`.
3.  Operate the assigned work in Trainz, entering completion times and
    marking tasks Done.
4.  Run `switchlist1.py` again when you finish or want to update the
    score.
5.  When ready to advance, select New Day; completed work is archived,
    waiting work may become ready, and new work is assigned.
6.  Reopen/continue the viewer and operate the next day's work.

## Gameplay

The default setting is designed to accommodate a 'session' lasting 5
days. Days 1--4 use the normal task-generation system. On Day 5, newly
generated work consists only of small, one-step deliveries from an
off-map portal to an on-map consumer. From Day 6 onward, no new work is
generated, allowing the player to finish outstanding tasks.

The switchlist is designed to accommodate a mixture of tasks, between
delivering loads to industries from portals, to picking up loads for
sending to portals, to handling industry chains where you spot empties,
then subsequently pick up those loads and deliver them to another
customer on the route map. For an on-map shipment, the switchlist can
generate:

-   Spot Empties --- Producer
-   Pickup Load --- Producer
-   Deliver --- Consumer

These are separately scored tasks, even though they belong to one
physical shipment. (A shipment may consist of several tasks sharing the
same shipment ID. For example, Spot Empties → Pickup Load → Deliver.
Each individual task also has its own task number.)

After a delivery is made and a shipment is completed, the switchlist
does not generate a task to pickup empties. The user may handle the
empties however they like -- leave them there, move to the yard, or
assemble and exit the route via a portal. This is not tracked.

The default program recognizes Juniata and Grafton as off-map portals. A
portal represents traffic entering or leaving the route. You will need
to change these names in the `switchlist1.py` python file if your route
uses different portals. (See below.)

switchlist1: Each time you initiate a new session (including continuing
prior sessions that are unfinished), you will first run
`switchlist1.py`. This program will prompt you by asking whether you are
starting a new playthrough, continuing an existing playthrough, and
whether you are starting a new day or continuing the day already
underway, as follows:

-   New session/playthrough --- resets the previous playthrough and
    starts Day 1 at 0830. Important note: selecting this option deletes
    all prior session data!
-   New day --- advances one day, archives completed tasks, unlocks
    eligible waiting tasks, calculates the score, and generates new
    work.
-   Continue current day --- archives completed work and updates the
    score, but does not advance the day or generate a new day's work.

switchlist_viewer: once you have run `switchlist1.py`, next you will run
the switchlist_viewer. This will pull up a new html window showing the
tasks currently assigned. The html window will be in front of other
windows, but can be minimized or maximized by clicking f9 on your
keyboard. You can end the program completely by right-clicking the
taskbar and clicking close.

In the switchlist_viewer, you will see one row for each task. Some rows
will start greyed out, indicating that they have been assigned but are
not yet marked as 'ready', for activity. For example, if you have a task
to 'spot empties' at industry X, and later 'pickup load' at industry X
and then deliver that to industry Y, the pickup and delivery will not be
'ready' until you have first spotted empties, marked that task as done,
and waited for the start of the next day. (You can override this by
clicking 'active' on any task.)

When marking a task as completed, the user must enter the day of
completion (1, 2, etc) and the time (in military time: for example,
1100, 1300, 1600). For the scoring, the game only considers hours, but
the minutes may be useful for the user's own tracking. When you check
"completed," the task will be greyed out. However, you can uncheck the
box if you made a mistake and the line will reappear. Be sure to fill in
the day and time of completion, and make sure the values make sense --
i.e. make sure the day and time are not prior to the start-time you
indicated when you ran the switchlist, and make sure not to mistakenly
enter the time for day and vice-versa -- easy to do!

The viewer includes three user-set fields for tracking / notetaking:

-   Marking the task as "active" makes it easier to scan which tasks you
    are working on. Active is primarily a user-tracking field; but it
    also overrides the Ready shading, allowing a not-yet-ready task to
    be treated visually as active.
-   Similarly, "assignment" is where you can type the driver's name, and
    perhaps additional info like what order, or loco number. This is
    saved but does not contribute to score or anything else within the
    program. You can leave it blank if you want.
-   Partial is a free-form tracking field for noting that part of a task
    has been completed (for example, 4 of 8 cars). It has no effect on
    task completion or scoring, and can be left blank if unneeded.

The switchlist viewer shows a score for the session at the bottom, which
is only updated when you run the `switchlist1.py` program, so it won't
be updated on the fly when you mark tasks as completed.

Scoring is as follows, points are per car per task. An 8-car shipment
completing three separately scored stages can therefore represent
substantial points.

  Completion time      Points per car
  ------------------ ----------------
  Less than 1 day                   4
  Less than 2 days                  3
  Less than 3 days                  2
  Less than 4 days                  1
  4 days or more                    0

The default setting allows the user to track certain mistakes and
incorporate these in their score -- this is entirely based on the 'honor
system' and the user's input. Major derailments are scored -250, and
minor incidents are scored as -75. (These scores will only be added up
and shown at the end of the full playthrough.) A minor incident could
include small derailments caused by a switch thrown under a train,
coupling too fast, or accidentally clipping into another train without
derailing. Major derailments -- well, you know 'em when you see 'em!

## Installation

Please start by downloading all the files in the Github directory to
your hard drive. To ensure the files work correctly and are not
overwritten when Trainz updates, make sure to download the files into a
new folder that is completely outside any Trainz game or asset folder.
There are no executable files in the folder, so your firewall and virus
software should not give any problems.

The files you will need are: - `switchlist1.py` -
`switchlist_viewer.py` - `pb-industry-list.xlsx` -
`current_switchlist.xlsx` - `completed_tasks.xlsx` -
`score_summary.xlsx` - `switchlist_status.json` - `game_state.json`

The switch list program requires Python to run. You should download the
latest version of python. I recommend VSCode for running python and
editing python scripts on PC. This readme will not cover python
installation, as there are many guides online if you run into problems.

Once you have everything downloaded and python installed, you can run
the programs from VSCode or the command line. You will also need to
ensure the following are installed inside your python environment:

``` bash
pip install pandas
pip install openpyxl
pip install pywebview
pip install keyboard
```

There are two python programs in this folder. - `switchlist1.py` -
`switchlist_viewer.py`

`current_switchlist.xlsx`, `completed_tasks.xlsx`, `score_summary.xlsx`,
`switchlist_status.json`, and `game_state.json` are working files
maintained by the programs. You should NOT edit or delete them during an
active playthrough, and in general there is no need to touch them at
all. Customize `pb-industry-list.xlsx` instead.

Files you customize - `pb-industry-list.xlsx` - optionally the .py
programs Files the program maintains - everything else

## Initial setup -- customizing your industry list

The file '`pb-industry-list.xlsx`' is an Excel file with a list of
industries you should edit to reflect your own route's situation. Delete
any rows you don't need. Here are the columns that may need some
explanation: - commodity: For each industry, each commodity should have
its own row, and a car-type assigned. - produce_consume: consumer rows
will generate tasks to deliver goods, while producer rows will generate
tasks to first spot empties and then pickup goods. (Note: consumer rows
will not generate tasks to pickup empties. This is left to the user's
discretion.) - car_type: Self-explanatory. If multiple car types are
supported, you can add a separate row for each car type for a given
commodity. - mandatory_start: this determines whether the
industry-commodity pair will always generate new tasks on the start of a
new playthrough. Possible values are "yes" and "no." - the min_carloads
and max_carloads should be set to a reasonable level based on the length
of the loading track or other relevant consideration. (Note: the
industries are all assumed to be set up as "JR Multi Industry II" tracks
with each good produced and consumed entirely independently; producing
queues should always be full, and consumption queues should always be
empty.) - source_mode: this determines whether the industry can serve
other customers on the map, and whether it serves fixed customers (up to
a max of 2 customers on the map). Possible values are
"fixed_on_map_only," "on_map_ok," and "off_map_ok." "on_map_ok" allows
the program to use a matching on-map industry as a source/destination
when one is available, while "off_map_ok" means the commodity is instead
sourced from or sent to an off-map portal. If you designate
"fixed_on_map_only," be sure to paste the exact name of the industry it
will go to in at least the first fixed_partner_1. Commodities must also
match exactly. For commodities that can go off map or come from off the
map, these will be set randomly to come from/go to either "Grafton
portal" or "Juniata portal." You can customize the names/number of
portals. - first fixed_partner_1: name of industry that a commodity must
be delivered to or be sourced from, for on_map shipments. Industry and
commodity names must match exactly. - first fixed_partner_2: if a split
is allowed, this is a second fixed partner. Industry and commodity names
must match exactly. - allow_split: this determines whether cars picked
up at an industry can be delivered to more than one end customer.
Possible values are "yes" and "no." - split_probability: this determines
the probability that a given delivery will be split. Values from 0 to 1.
Will only function if allow_split set to "yes."

## Optional customization

You may edit `switchlist1.py` to customize certain features such as the
html window size, text colors, background colors, etc. In addition, you
may want to edit the following:

-   portal names (by changing the line PORTALS = \["Juniata Portal",
    "Grafton Portal"\])
-   number of tasks generated (edit the line: target_total =
    random.randint(10, 15))
-   five-day session structure
-   scoring values
-   incident penalties (default 250 and 75)
